# Mina Tests Stage 7C — open enrollment and release preparation

21 October 2026. Implementation and local checks only. No cloud resources, live configuration, publication, deployment or distribution changed. This document supersedes Stage 7B invitation-only admission. Historical Stage 7A/6 evidence does not establish release approval.

## Architecture implemented

Any registered Flux user may enroll in an approved, active experiment in the matching Firebase project after server eligibility and explicit consent. There is no participant cap, UID allowlist, globally updated participant count or private invitation requirement. Anonymous Firebase identities cannot enroll through deployed callables. Legacy enrollment retains the same release/adult checks; administrator draft rehearsal stays separate.

`environment` is derived from the trusted server Firebase project: `flow-9d714` is production; separate projects are staging; the local Functions emulator is development. Client input cannot choose it. Staging Android uses explicit non-production Firebase options and a separate `com.chiasmatic.flow.staging` application ID, guarded before Firebase initialization. Gradle requires the staging entry point and staging define together, selects a separate package, and removes Firebase native auto-initialization in the staging manifest. Runtime checks reject the production application ID/project before explicit staging initialization. Use separate Auth users, Firestore, Storage, IAM, secrets, website deployment and capability evidence; never copy participant data. Public discovery requires `visibility: public`, `publicationApproved: true` and matching environment. Internal definitions can be executed only in a separate staging project. Project isolation replaces production UID policies.

Lifecycle: draft (unapproved), testing (internal staging), published (approved public or staged), paused, completed. `visibility` is independent of `enrollmentEnabled`. Only published/testing with an explicitly true switch permits NEW enrollment. A published experiment can stay discoverable with enrollment disabled. Pausing/completing hides no existing owner record and changes no pinned assignment. Draft/unapproved/internal production roots are not publicly discoverable or enrollable, even by known ID. Missing new root fields fail closed; any future migration needs reviewed explicit metadata, not a blanket enabling script. Remove obsolete private pilot policy documents only through a separately approved cleanup; they no longer authorize anything.

Enrollment uses a deterministic per-experiment/user record and transactional reads of experiment/version/capabilities, per-user deletion tombstone and existing enrollment. It writes only that participant record. Independent participants do not contend on a shared write. Duplicate enrollments return the existing immutable assignment; retries cannot rerandomize. Age >=18 applies to validation/publication/enrollment and legacy fallback. Version/asset hashes and consent are pinned. Server local-calendar scheduling and completion validation remain authoritative.

A Firestore creation trigger counts historical admissions asynchronously in 256 deterministic shards with event-ID dedupe receipts. At-least-once delivery cannot double count a retry; counters never authorize admission. Counts include withdrawals/deleted admissions and start only when the trigger is deployed. Existing documents are not backfilled. Empty metrics show unavailable, not zero. They are not current active/completed or website signup totals. Receipts store no UID/answers; keep dedupe receipts across retry/replay. Reconciliation/backfill, if needed, must be separately designed and approved with stable enrollment dedupe identities.

Catalog/admin queries use indexed cursor pages (20 default, callable maximum 50). Admin scientific locking uses bounded existence queries instead of enrollment writing the editor document. New enrollment progress stores task completion/session state on its own record, so normal state refresh avoids scanning all responses; older records retain a compatibility fallback. The owner continuation UI initially streams 50 records and can expand in batches of 50; this repeats prior owner reads and is a remaining optimization for unusually many simultaneous studies. Dashboard count reads are bounded 256 shards per experiment (up to 5,120 reads/page); cache or scheduled materialization is appropriate at high admin traffic. It does not affect participant admission.

Withdrawal remains accessible with confirmation, native-session shutdown, pending queue cancellation and retryable idempotent server withdrawal. Research deletion must finish before Firebase Auth deletion; tombstones prevent stale concurrent writes, and both outboxes/native observations/local research caches are cleared. Consent history, assignments, response records and research results remain server-owned and participant-isolated. Website email marketing identities are separate from Auth research identities: optional email confirmation must not be represented as research consent/enrollment or unified deletion.

Functions explicitly use 1 CPU / concurrency 80 / maxInstances 20 per callable. This is an operational ceiling, not an admission cap. At assumed200ms, an optimistic theoretical8000 requests/s per callable is NOT guaranteed; CPU, connection pools, cold starts, regional quotas and Firestore contention can reduce it. At 1 million participants, one million morning requests in 10 minutes is 1,667/s before retries or multiple calls. Set load-test SLOs using measured p95/p99 and worst synchronized windows; maxInstances saturation queues then rejects requests. Clients must retry safely with backoff; preserve task/calendar semantics. Confirm deployed memory and quotas; do not assume the maxInstances 20 setting supports a million-user launch.

Root reads are shared but no per-enrollment root writes. Administrative switch changes invalidate in-flight transactions safely and can cause retries. Per-participant progress serializes that user's concurrent tasks, which is intentional integrity protection. Metrics shard transactions may contend during large bursts; measure retries and raise shard count/version or move aggregation off-path if needed. Retry failures do not block admission but can delay counts. Receipts and responses grow linearly; define retention/erasure and reconcile metrics. Firestore indexes include catalog environment/visibility/approval/status and owner engine/status queries. Exempt large protocol/response/maps and unused monotonic timestamps to reduce index fanout/hotspots. No blanket timestamp exemption on fields actually queried. Deploy/verify indexes before relying on new queries; ramp new traffic gradually (500/50/5 guidance), measure hot ranges and regional quotas.

Monitoring essentials: callable count/errorcode/p50/p95/p99, cold-start and429/503 rate, transaction retries, writes/reads and cost budgets, trigger failures/lag/duplicate receipt rate, catalog page/missing-index errors, consent-to-enrollment conversion, eligible rejection reasons in coarse categories, start-to-save and morning completion/missed-window rates, outbox age/retries, withdrawals/deletion failure/latency and stale-write rejection. Use restricted structured request/event IDs, never answers/email/consent text/tokens in logs. Add Crashlytics or equivalent for Dart/native crashes and foreground-service failures; it is NOT currently proven configured. Budget alerts and crash monitoring require separate configuration approval.

App Check remains disabled in existing callable options. Registered authentication and bounded validated requests are present but do not stop scripted abuse. Before a broad public launch, validate Play Integrity on the final signed app, monitor App Check metrics, then explicitly approve enforcement. Consider per-account/action rate limits and abuse alerts (not participant caps or shared global admission counters); align with legitimate offline retry. Test unauthenticated/anonymous rejection and invalid/replayed submissions through actual deployed callables. Website acquisition retains its existing separate rate limits. Missing load tests and unenforced App Check are release risks, not evidence of proven million-user capacity.
